# GYMLLM

GYMLLM is an internal HR assistant for **The Yard**, a multi-branch gym organization. It uses retrieval-augmented generation (RAG) to answer HQ HR questions with concise, practical responses grounded in the organization’s knowledge base.

The system is designed for everyday HR operations, including recruitment and onboarding, employee and credential verification, payroll and commission processing, labor-law compliance, contracts, workplace investigations, dispute resolution, benefits, health and safety administration, and branch operations.

> **Data note:** The included knowledge base is synthetic and intended for development, evaluation, and demonstration purposes. It must not be treated as a source of real employment, legal, payroll, or medical advice.

## Highlights

- Asynchronous FastAPI backend with a streaming response endpoint.
- Gradio chat interface for HQ HR users.
- Retrieval over a Chroma vector store using OpenAI embeddings.
- Conversation history passed from the frontend to the backend for context-aware answers.
- Markdown-based knowledge base with document-type metadata.
- DVC tracking for the knowledge-base directory.
- Evaluation tooling for retrieval quality and generated-answer quality.
- Docker Compose setup for running the backend and frontend as separate services.
- Python 3.12 and `uv`-based dependency management for the application services.

## Architecture

```text
                         ┌─────────────────────────┐
                         │      Gradio frontend    │
                         │      localhost:7860     │
                         └────────────┬────────────┘
                                      │ HTTP streaming
                                      │ POST /GYMLLM
                         ┌────────────▼────────────┐
                         │      FastAPI backend    │
                         │      localhost:8000     │
                         └────────────┬────────────┘
                                      │
                     ┌────────────────▼────────────────┐
                     │       RAG answer pipeline       │
                     │  retrieve top-k context + LLM   │
                     └────────────────┬────────────────┘
                                      │
              ┌───────────────────────▼───────────────────────┐
              │ Chroma vector store                            │
              │ text-embedding-3-large embeddings              │
              └───────────────────────┬───────────────────────┘
                                      │
              ┌───────────────────────▼───────────────────────┐
              │ Markdown knowledge base                         │
              │ company, owners, branches, policies, employees  │
              └────────────────────────────────────────────────┘
```

The frontend sends the current question and prior conversation turns to the FastAPI service. The backend combines the user’s previous questions for retrieval, fetches the five most relevant documents from Chroma, inserts those documents into the HR system prompt, and streams the answer generated by `gpt-4.1-mini` back to the Gradio interface.

## Knowledge base

The knowledge base is stored as Markdown documents and tracked with DVC. Its main domains are:

- **Company main details** — corporate identity, registrations, executive structure, and company-wide compensation frameworks.
- **Owners** — stakeholder profiles, ownership interests, voting rights, and legal signatory information.
- **Branches** — facility profiles, branch leadership, capacity, shifts, and operating permits.
- **Policies and compliance** — handbooks, trainer conduct, safety regulations, and dispute procedures.
- **Employees** — structured employee metadata, biographies, contracts, certifications, compensation, and leave records.

The tracked snapshot contains **222 Markdown documents**. The reported corpus statistics are approximately **362,908 characters**, **103,270 `o200k_base` tokens**, and **235 indexed chunks** after splitting.

### Rebuilding the vector store

`backend/implementation/ingest.py` loads Markdown files from `knowledge-base/`, adds the parent folder as `doc_type` metadata, splits the documents with a `tiktoken`-based splitter, and writes the resulting Chroma collection to `backend/vector_db/`.

The current ingestion configuration uses:

- Encoding: `o200k_base`
- Chunk size: 500 tokens
- Chunk overlap: 100 tokens
- Embedding model: `text-embedding-3-large`
- Expected embedding dimensions: 3,072

From the repository root, run:

```bash
cd backend
uv run python implementation/ingest.py
```

The ingestion script replaces the existing Chroma collection before creating the new one, so rerun it whenever the knowledge base changes.

## Evaluation

The evaluation pipeline measures both retrieval and generation quality.

### Retrieval metrics

For each benchmark question, the evaluator checks whether expected entities, policy terms, dates, and other keywords appear in the retrieved documents. It reports:

- **MRR** — Mean Reciprocal Rank of keyword matches.
- **nDCG** — normalized discounted cumulative gain using binary relevance.
- **Keyword coverage** — percentage of expected keywords found in the retrieved context.

### Answer metrics

Generated answers are assessed with an LLM-as-a-judge using Pydantic-validated structured output. Each answer receives a score from 1 to 5 for:

- **Accuracy** — factual correctness against the reference answer.
- **Completeness** — coverage of required conditions, exceptions, and procedural steps.
- **Relevance** — directness and freedom from unsupported or off-topic content.

The benchmark generator creates questions in five categories: `direct_fact`, `spanning`, `temporal`, `policy_procedural`, and `compliance_conflict`. It uses structured responses, category balancing, and anti-leakage instructions to keep generated questions realistic and grounded in the source material.

The project’s reported evaluation results are approximately **83% retrieval coverage**, **4.89/5.0 answer accuracy**, and a **96% test pass rate** after moving from arbitrary chunking to header-aware chunking and tuning retrieval depth.

## Configuration

Create a `.env` file in the repository root. At minimum, the backend requires:

```dotenv
OPENAI_API_KEY=your_openai_api_key
```

The frontend also reads the following optional settings:

```dotenv
GOOGLE_API_KEY=your_google_api_key
BACKEND_URL=http://localhost:8000
```

When using Docker Compose, the frontend is configured automatically to reach the backend through the internal service address:

```text
http://backend:8000
```

Do not commit `.env` files or real employee, payroll, identity, or legal data to the repository.

## Run with Docker Compose

From the repository root:

```bash
docker compose up --build
```

The services are exposed at:

- **Frontend:** http://localhost:7860
- **Backend health check:** http://localhost:8000/
- **FastAPI Swagger UI:** http://localhost:8000/docs
- **FastAPI ReDoc:** http://localhost:8000/redoc

To stop the services:

```bash
docker compose down
```

The Compose configuration builds the backend and frontend independently, loads environment variables from the root `.env` file, and makes the frontend depend on the backend service.

## Run locally without Docker

Install the service dependencies with `uv`:

```bash
cd backend
uv sync

cd ../frontend
uv sync
```

Start the backend in one terminal:

```bash
cd backend
uv run uvicorn app:app --host 0.0.0.0 --port 8000
```

Start the frontend in another terminal:

```bash
cd frontend
uv run python frontend.py
```

Then open http://localhost:7860.

For a local frontend process, `BACKEND_URL` should normally be set to:

```dotenv
BACKEND_URL=http://localhost:8000
```

## API

### `GET /`

Returns a basic service-health response and links to the API documentation.

### `POST /GYMLLM`

Accepts a question and an optional list of previous conversation messages. The response is streamed as generated text.

Example request:

```json
{
  "hr_question": "Who is the current branch manager of Khalda branch?",
  "history": [
    {
      "role": "user",
      "content": "I need information about the Khalda branch."
    },
    {
      "role": "assistant",
      "content": "What would you like to know?"
    }
  ]
}
```

Example with `curl`:

```bash
curl -N -X POST http://localhost:8000/GYMLLM \
  -H "Content-Type: application/json" \
  -d '{
    "hr_question": "Describe the maximum permitted workweek and daily working hours for operational staff",
    "history": []
  }'
```

## Synthetic data generation

The repository includes scripts for generating development data and benchmark questions.

Generate synthetic employee profiles:

```bash
uv run python generating-data/generate_employees.py
```

Generate the benchmark JSONL file from the knowledge base:

```bash
uv run python generating-data/generate_tests.py
```

The benchmark generator uses an asynchronous OpenAI client and writes questions to `tests/tests.jsonl`. The generated employee profiles are written under `knowledge-base/employees/`.

## Running an evaluation

The evaluator accepts a benchmark row number and prints retrieval metrics together with the generated answer and LLM-judge scores:

```bash
cd evaluation
uv run python eval.py 0
```

The evaluation modules expect the benchmark file at `tests/tests.jsonl` and the vector store to be available to the backend implementation. Make sure the knowledge base has been restored and ingestion has completed before running evaluation.

## Design notes

- Answers are instructed to stay grounded in retrieved source material and to say when the requested information is unavailable.
- Retrieval uses the current question together with previous user turns, while the generated response receives the structured conversation history.
- The frontend supports streaming output, message history, copy-to-clipboard, quick example questions, and a light/dark theme toggle.
- The backend uses `StreamingResponse` with an `async` generator so the UI can display partial answers as they are generated.
- DVC keeps the knowledge-base payload separate from the Git repository while preserving a reproducible pointer to the tracked dataset.
